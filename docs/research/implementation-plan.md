## Як читати

Кожен пункт описано шістьма полями: **Мета** (що зміниться у спостережуваних термінах),
**Кроки** (конкретні правки з реальними шляхами), **Перевірка** (команда, що доводить
результат), **Ризик**, **Залежності**, **Розмір** (S ≤ пів дня, M ≈ день, L > дня).

Для фронтових пунктів вказано рівень авторитетності за скілом `frontend-ui-architecture`:
**SPECIFIED** (вимога React/Next.js), **CONVENTION** (усталена практика без офіційного
джерела), **UNSPECIFIED** (рішення проєкту). Там, де рівень не SPECIFIED, план не виносить
вироку — він формулює питання, і ці питання зібрані в розділі «Питання до користувача».

Незмінні обмеження, які діють у кожному пункті:

- `*/src/vendor/**` і `server/src/db/migrations/**` не редагуються. Контракти правляться
  тільки в `server/src/vendor/shared`, міграції — тільки через `pnpm db:generate`.
- `INSIGHTS.md` — append-only, через скіл `engineering-insights`.
- Service locator (`this.container.*` у тілі методу) лагодиться **при дотику до файлу**,
  ніколи окремим sweep-ом. Тому П.6 не має власного батча — він їде разом з іншими.
- Правило `dependency-cruiser` переводиться з `warn` у `error` **тим самим комітом**, який
  закриває його останнє порушення, і `OUTSTANDING`-коментар при цьому зникає.

## П.2 — `response`-схеми на ручках API

**Мета.** Кожна не-SSE ручка віддає тіло, звірене з Zod-контрактом; `fast-json-stringify`
вмикається; розходження сервера з контрактом падає в CI, а не в браузері користувача.

**Кроки.** Сьогодні `grep 'response:' src/modules/*/routes.ts` дає 0 на 48 ручок. Контракти
здебільшого вже існують у `server/src/vendor/shared/contracts/` — дописувати треба лише
п'ять. Розподіл:

*B5 — контракт уже є, додається лише `response: { 200: … }`:*

| Ручка | Файл | Контракт |
|---|---|---|
| `GET /agents`, `/agents/:id`, `POST`, `PUT /agents/:id` | `modules/agents/routes.ts` | `Agent` / `z.array(Agent)` (`contracts/knowledge.ts:176`) |
| `GET /agents/:id/versions` | там само | `z.array(AgentVersion)` (`knowledge.ts:218`) |
| `GET /agents/:id/models`, `GET /providers/:id/models` | там само | `z.array(ModelInfo)` (`vendor/shared/adapters.ts`) |
| `GET /repos`, `POST /repos`, `POST /repos/:id/refresh` | `modules/repos/routes.ts` | `Repo` / `z.array(Repo)` (`platform.ts:140`) |
| `GET /repos/:id/pulls` | `modules/pulls/routes.ts` | `z.array(PrMeta)` (`platform.ts:157`) |
| `GET /pulls/:id` | там само | `PrDetail` (`platform.ts:213`) |
| `GET /pulls/:id/comments`, `POST /pulls/:id/comments` | там само | `PrReviewComment` (`platform.ts:227`) |
| `POST /pulls/:id/review` | `modules/reviews/routes.ts` | `ReviewRunResponse` (`review-api.ts:52`) |
| `GET /pulls/:id/runs` | там само | `z.array(RunSummary)` (`trace.ts:100`) |
| `GET /runs/:id/trace` | там само | `RunTrace` (`trace.ts:77`) |
| `GET /pulls/:id/reviews` | там само | `z.array(ReviewRecord)` (`review-api.ts:23`) |
| `GET /settings`, `PUT /settings` | `modules/settings/routes.ts` | `Settings` (`platform.ts:99`) |
| `GET /settings/secrets-status` | там само | `SecretsStatus` (`platform.ts:126`) |
| `POST /settings/test-connection` | там само | `ConnTestResult` (`platform.ts:116`) |

*B6 — контракту немає, спершу дописати його в `server/src/vendor/shared/contracts/`:*

1. `ActiveRun` → `contracts/trace.ts`. Форма вже описана **в клієнті**
   (`client/src/lib/hooks/reviews.ts:19`, локальний `interface ActiveRun`) — це і є доказ,
   що контракт мав бути спільним. Після додавання прибрати локальний інтерфейс і читати
   тип з `@devdigest/shared`.
2. `OkResponse` = `z.object({ ok: z.boolean() })` → `contracts/platform.ts`. Покриває
   `DELETE /runs/:id`, `POST /runs/:id/cancel`, `DELETE /reviews/:id`.
3. `DeletedResponse` = `z.object({ deleted: z.string() })` → там само. Покриває
   `DELETE /agents/:id`, `DELETE /repos/:id`.
4. `FindingActionResult` = `z.object({ finding: FindingRecord, memoryId: z.string().nullish() })`
   → `contracts/review-api.ts` (поруч із `FindingRecord`). Покриває
   `POST /findings/:id/accept|dismiss` (`modules/reviews/routes.ts:144`).
5. `WorkspaceInfo` → `contracts/platform.ts`. Форму взяти з
   `modules/workspace/routes.ts:22` як є (`workspaceId`, `cloneDir`, `repos[]`).
6. `PollResult` = `z.object({ synced: z.number().int(), reviewTriggered: z.boolean() })`
   → `contracts/platform.ts`, для `POST /repos/:id/poll`.

Дзеркала `client/src/vendor/shared` синхронізуються після правки джерела — руками їх не
редагувати.

**Окремо: `GET /runs/:id/events`** — SSE, тіла-відповіді немає. `response`-схема до неї не
додається; лишити коментар у коді, щоб наступний не шукав пропуск.

**Перевірка.**
```sh
pnpm --dir server exec vitest run test/routes-smoke.test.ts test/contracts.test.ts
pnpm --dir server exec vitest run .it.test    # потребує Docker
grep -c 'response:' server/src/modules/*/routes.ts   # має зрости до ~44
```
Плюс ручна перевірка однієї ручки на реальному стеку: `curl -s localhost:3001/repos | jq`.

**Ризик.** Головний і недооцінений: **Zod-серіалізатор вирізає невідомі ключі**. Якщо
хендлер сьогодні повертає поле, якого немає в контракті, а клієнт його читає — після
ввімкнення схеми воно мовчки зникне з відповіді. Тому кожну ручку вмикати разом із
перевіркою, що саме читає клієнт (`client/src/lib/hooks/*`). Виняток безпечний за
побудовою: `Settings` — це `.passthrough()`.

Другий ризик — `RunTrace`. Трейси зберігаються як jsonb-документ і віддаються дослівно
(`run_traces.trace`), тож схема відповіді парситиме документи, **записані старішим кодом**.
Будь-яке нове поле в `RunStats`/`RunTrace` має бути `nullish()`, а не `nullable()` — інакше
`GET /runs/:id/trace` почне кидати `Required` на всіх старих трейсах. Правило записане в
`server/INSIGHTS.md`; прочитати той запис перед правкою `contracts/trace.ts`.

Третій: помилка серіалізації віддає 500 через `isResponseSerializationError` у
`src/app.ts:120` — тобто зламана схема перетворює робочу ручку на 500. Звідси вимога:
жодна ручка не вмикається без тесту, що її дьоргає.

**Залежності.** `pulls`-ручки — після B4 (інакше та сама функція переписується двічі).
**Розмір.** B5 — M, B6 — M. **Скіл:** `zod`, `fastify-best-practices`.

## П.3 — транзакції на мультизаписних потоках

**Мета.** Падіння посеред багатокрокового запису не лишає PR без файлів: або застосовано
все, або нічого.

**Кроки.**

1. Головне місце — `server/src/modules/pulls/routes.ts:232-265`: `delete(prFiles)` →
   `insert(prFiles)` → `delete(prCommits)` → `insert(prCommits)` → `update(pullRequests)`,
   п'ять окремих операцій поспіль. Загорнути в один `db.transaction(async (tx) => …)`.
   Транзакцію володіє репозиторій (`onion-architecture`: сервіс не приймає тип транзакції
   Drizzle як параметр), тож після B4 це один метод
   `PullsRepository.replaceDetail(prId, files, commits, stats)`.
2. Другорядне — `server/src/modules/settings/routes.ts:52-61`: цикл upsert-ів по ключах
   налаштувань. Часткове застосування патча лишає налаштування напівзбереженими. Одна
   транзакція на весь `PUT /settings`.
3. Третє — збереження результату ревʼю: `insertReview` + `insertFindings` — два виклики
   поспіль (`modules/reviews/run-executor.ts:219` і `:230`). Падіння між ними лишає
   review без findings, тобто «ревʼю на 0 зауважень», що виглядає як успіх. Обидва
   `insert` — в одну транзакцію на рівні `ReviewRepository`.

**Перевірка.** Тест на відкат у `server/test/pulls-detail.it.test.ts` (новий,
`.it.test.ts` — бо потрібна справжня БД): імпортувати деталі PR, далі підсунути GitHub-клієнт,
що кидає після віддачі `files`, і перевірити, що `pr_files` лишились попередніми, а не
порожніми.
```sh
pnpm --dir server exec vitest run .it.test
```

**Ризик.** Блок у `pulls` обгорнутий `try/catch`, який деградує до збережених даних. Зараз
часткове падіння дає порожній список файлів **і** catch, що віддає вже стерте. З транзакцією
поведінка стає кращою, але це зміна поведінки — відобразити її в тесті явно, бо «порожній
список файлів» сьогодні може десь читатись як норма.

**Залежності.** Робиться всередині B4, не окремим PR: та сама функція.
**Розмір.** S у складі B4. **Скіл:** `drizzle-orm-patterns`.

## П.4 — винести логіку й SQL із route-хендлерів `pulls` і `workspace`

**Мета.** `modules/pulls/routes.ts` скорочується з 374 рядків до тонкого шару «розпарсити →
викликати сервіс → віддати DTO»; імпорт PR стає тестованим без HTTP-сервера;
`pnpm arch` втрачає 4 попередження `routes-dont-touch-persistence`.

**Кроки.**

1. Створити `server/src/modules/pulls/repository.ts` за зразком
   `modules/reviews/repository.ts` (той делегує у `repository/*.repo.ts`, згруповані за
   агрегатом). Методи: `listByRepo`, `upsertMany`, `getPull`, `replaceDetail`,
   `backfillStats`, `severityTallyByPr`, `costByPr`, `latestScoreByPr`.
2. **Спершу перевірити, що вже є.** `modules/reviews/repository/pull.repo.ts` уже містить
   `getPull`, `getRepo`, `getPrFiles`, `markReviewed` — тобто агрегат PR частково живе в
   модулі `reviews`. Не дублювати: перенести ці функції у новий `pulls`-репозиторій і
   віддати `reviews` доступ через контейнер (`container.pullsRepo`), як уже зроблено з
   `container.reviewRepo` і `container.agentsRepo` (`platform/container.ts:88`). Імпорт
   `modules/reviews/*` → `modules/pulls/repository.ts` був би порушенням
   `no-cross-module-internals`.
3. Створити `server/src/modules/pulls/service.ts`: `listPulls(workspaceId, repoId)` і
   `getDetail(workspaceId, prId)`. Уся деградація «немає токена → віддаємо збережене»
   переїжджає сюди; логер передається як порт `Logger`, а не `req.log`
   (зразок — `modules/reviews/run-executor.ts:22`).
4. `modules/workspace/routes.ts` — те саме в мініатюрі: `workspace/service.ts` +
   читання репозиторію репо через `container`. Модуль крихітний, тож окремий
   `repository.ts` тут зайвий — узяти наявний доступ до `repos`.
5. Дорогою, **не окремо**: `this.container.*` у тілах методів файлів, яких торкаємось,
   резолвиться в конструкторі (П.6).
6. Зареєструвати нічого не треба: `modules/index.ts` уже реєструє обидва модулі.

**Перевірка.**
```sh
pnpm --dir server arch        # routes-dont-touch-persistence: 4 → 0, правило в `error`
pnpm --dir server exec vitest run --exclude '**/*.it.test.ts'
pnpm --dir server exec vitest run .it.test
```
Плюс новий гермет-тест `server/test/pulls-service.test.ts` на мок-адаптерах
(`src/adapters/mocks.ts`): деградація без GitHub-токена має віддавати збережені PR.

**Ризик.** `GET /repos/:id/pulls` — найгарячіша ручка UI, і в ній зосереджено чотири
окремі похідні (score, cost, findings-tally, derived status). Тальї по findings тримаються
на join до `reviews`, бо `findings` **не має `workspace_id`** — при переносі в репозиторій
цей join не можна «спростити» до фільтра по `review_id`, це перевірка тенантності, а не
оптимізація (записано в `server/INSIGHTS.md`). Крос-воркспейсна фікстура в `.it.test.ts` —
єдине, що ловить регресію тут.

**Залежності.** Блокує П.2 для `pulls`-ручок. Вбирає П.3 і П.8.
**Розмір.** L. **Скіл:** `onion-architecture`, `fastify-best-practices`.

## П.5 — 17 попереджень `pnpm arch`

**Мета.** Лічильник падає з 17 до 3–5, і щонайменше три правила переходять у `error`.

**Кроки** — у порядку зростання ціни.

*B1 — типи рядків (3 попередження `no-orm-outside-persistence`).* Три файли імпортують
`db/schema` **виключно заради типів**: `modules/reviews/run-executor.ts:58`
(`typeof schema.repos.$inferSelect`), `modules/reviews/diff-loader.ts:17` (те саме),
`modules/repos/helpers.ts:44` (те саме). Скіл називає інлайновий `$inferSelect` поза
`db/rows.ts` витоком. Додати `export type RepoRow = typeof t.repos.$inferSelect;` у
`server/src/db/rows.ts` (там уже живуть `AgentRow`, `PullRow`, `FindingRow`, `AgentRunRow`)
і замінити три імпорти. Зміна суто типова, рантайм не зачіпає.

*B2 — константи й job-kinds (3 попередження).*
`adapters/astgrep/index.ts:25` і `adapters/depgraph/index.ts:20` імпортують `SUPPORTED_EXT`
(астгреп — ще й `MAX_SIGNATURE_CHARS`) з `modules/repo-intel/constants.ts`: адаптер знає про
модуль, тобто стрілка залежності дивиться назовні. Це не константи модуля — це властивості
мови, тож їм місце в ring 0. Перенести `SUPPORTED_EXT`, `EXCLUDED_DIRS`, `MAX_SIGNATURE_CHARS`
у новий `server/src/platform/source-files.ts` із заголовком, що прямо відносить файл до
**чистої** половини `platform/` (скіл вимагає такої позначки для кожного нового файлу в
`platform/`). `modules/repo-intel/constants.ts` ре-експортує їх, щоб не правити десятки
місць одразу.
Окремо: `modules/repos/service.ts:14` тягне `INDEX_JOB_KIND`/`REFRESH_JOB_KIND` із
repo-intel — це міжмодульна координація, тож ключі задач переїжджають у
`modules/_shared/job-kinds.ts` (ring 1, обидва споживачі — ring 1).
Після цього `adapters-dont-know-modules` і `no-cross-module-internals` мають 0 порушень →
обидва в `error` тим самим комітом, `OUTSTANDING`-коментарі зникають.

*B3 — цикли (4 з 5).* Вузол `container.ts ↔ modules/repo-intel/service.ts`: контейнер
конструює `RepoIntelService(this)` (`platform/container.ts:117`), а сервіс тримає контейнер
і ходить у нього з методів. Факт, що робить лагодження дешевим: сервіс використовує лише
**чотири** члени контейнера — `config` (8 звернень), `jobs` (3), `codeIndex` (3), `git` (1).
Отже конструктор стає `constructor(deps: { config, jobs, codeIndex, git })`, контейнер
передає їх явно, і стрілка `service → container` зникає разом із чотирма циклами
(`service`, `pipeline/full.ts`, `pipeline/incremental.ts` — усі через той самий контейнер).
П'ятий цикл — локальний `modules/agents/helpers.ts ↔ modules/agents/repository.ts`;
розривається перенесенням спільного типу в `db/rows.ts` або в `agents/types.ts`.

*Лишається у `warn`:* `no-orm-outside-persistence` для
`modules/settings/feature-models.ts:41` (справжній запит у не-persistence файлі — лікується
разом із винесенням `settings/repository.ts`, окремий пункт поза цим планом) і чотири
route-файли, які закриває B4.

**Перевірка.** `pnpm --dir server arch` після кожного батча; лічильник лише спадає.
Регресія — будь-яке зростання. Конфіг `server/.dependency-cruiser.cjs` редагується разом
зі своєю копією в скілі `onion-architecture/enforcement/`, щоб вони не розʼїхались.

**Мета.** Читання, які сьогодні сканують таблицю цілком, ідуть по індексу.

`composed_reviews`, `multi_agent_runs`, `ci_runs`), індексувати передчасно.

extras-колбеку `pgTable`, далі `pnpm --dir server db:generate`. Міграція **не пишеться
руками** — це заборонений шлях.

**Перевірка.**

```sh
pnpm --dir server db:migrate
psql "$DATABASE_URL" -c "explain analyze select * from pr_files where pr_id = '…';"
```
В `explain` має зникнути `Seq Scan`. На порожній БД планувальник однаково вибере seq scan —
перевіряти на засіяній (`pnpm db:seed`) або не перевіряти взагалі, а вірити формі запиту.

**Ризик.** Кожен індекс сповільнює запис і займає місце; `pr_files` переписується цілком на
кожному відкритті PR (delete+insert), тож там індекс оплачується читаннями, але це не
привід додавати індекси «про запас». Друге: `db:generate` підхоплює **всі** незгенеровані
зміни схеми — перед запуском переконатись, що робоче дерево схеми чисте, інакше в міграцію
потрапить чуже.

**Залежності.** Немає. **Розмір.** S.
**Скіл:** `postgresql-table-design`, `drizzle-orm-patterns`.

## П.8 — N+1 у синхронізації PR

**Мета.** Синхронізація списку PR робить один запит до БД замість одного на кожен PR.

**Кроки.**

1. `modules/pulls/routes.ts:50-77` — цикл `for (const pr of pulls)` з окремим
   `insert().onConflictDoUpdate()` на кожен PR. Drizzle приймає масив у `.values([...])`
   разом з `onConflictDoUpdate`, тож увесь цикл стає одним запитом; у `set` для полів, що
   оновлюються, використовується ``sql`excluded.<col>` ``.
2. `modules/polling/routes.ts:31-59` — **той самий** upsert, скопійований удруге. Обидва
   місця замінюються одним викликом `PullsRepository.upsertMany(workspaceId, repoId, pulls)`.
   Тобто П.8 — це ще й дедуплікація, а не лише продуктивність.
3. `modules/pulls/routes.ts:94-112` (backfill діф-статистики) — тут **чесний** ліміт:
   кожна ітерація робить мережевий виклик `gh.getPullRequest`, і його не збатчити. Батчиться
   лише запис: зібрати результати й застосувати одним `insert … on conflict do update`.
   Ліміт `BACKFILL_LIMIT = 10` лишається.

**Перевірка.** Тест у `server/test/pulls-sync.it.test.ts`: мок GitHub віддає 50 PR; лічильник
запитів на мок-`Db` (або `pg_stat_statements`) має показати один upsert замість 50.
Простіший практичний доказ — час: `POST /repos/:id/poll` на репозиторії з 50 PR.

**Ризик.** `onConflictDoUpdate` з масивом і `excluded` легко написати так, що всі рядки
отримають значення **останнього** — це класична помилка, і вона тиха: дані є, вони
неправильні. Тест мусить перевіряти вміст двох різних рядків, а не лише кількість.

**Залежності.** Робиться в B4 (той самий файл і той самий новий репозиторій).
**Розмір.** S у складі B4. **Скіл:** `drizzle-orm-patterns`.

## П.13 — SSE і polling дублюють одне одного

**Мета.** Поки відкритий SSE-стрім, застосунок не опитує сервер тими ж питаннями.

**Кроки.**

1. `client/src/lib/hooks/reviews.ts:33` (`usePrActiveRuns`) і `:46` (`usePrRuns`)
   опитують кожні 4 с, поки щось виконується; паралельно `useRunEvents` (`:170`) тримає
   `EventSource` на ті самі запуски. Ввести прапорець «стрім живий» і вимикати
   `refetchInterval`, поки він піднятий.
2. Подію `result`/`error` зі стріму перетворювати на точкову інвалідацію через фабрику з
   П.12 — тоді дані оновлюються **за фактом події**, а не раз на 4 секунди.
3. `useRunEvents` накопичує події як `setEvents(prev => [...prev, parsed])` на кожен кадр.
   Для довгого логу це квадратична робота по ререндерах. Накопичувати в `useRef` і
   зливати в стан на `requestAnimationFrame` або пачками.

**Перевірка.** Новий тест `client/src/lib/hooks/reviews.test.ts` із замоканим `EventSource`:
поки стрім відкритий, `fetch` не викликається за таймером; після події `result` —
викликається рівно один раз. Плюс ручна перевірка на реальному ревʼю: у вкладці Network
не має бути запитів кожні 4 с під час активного запуску.

**Ризик.** Polling тут — не дублювання, а **резервний канал**: SSE рветься (проксі, сон
ноутбука, `es.onerror` у `:205` просто закриває джерело), і тоді опитування — єдине, що
доводить запуск до кінця. Тому вимикати polling можна лише на час **підтверджено живого**
стріму, з негайним поверненням до опитування на `onerror`/`close`. Прибрати polling
назовсім — регрес надійності, а не спрощення.

Друге: `useRunEvents` уже містить `eslint-disable react-hooks/exhaustive-deps` (`:212`) з
ключем-рядком `runIds.join(",")` замість масиву. Після П.1 це правило живе, тож будь-яка
правка хука має або зберегти свідоме придушення, або позбутись його чесно.

**Залежності.** Після П.12 (потрібна фабрика) і після П.15 (потрібні тести).
**Розмір.** M. **Рівень:** CONVENTION.

перевіркою на відсутні ключі, інакше вона створює борг замість того, щоб його закрити.

**Рівень:** UNSPECIFIED (сам i18n — вибір проєкту).

## П.15 — тестове покриття фронту

**Мета.** Логіка шару даних покрита тестами до того, як її почнуть змінювати.

**Кроки** — у порядку цінності:

1. `client/src/lib/api.ts` — нормалізація помилок: мережеве падіння → `ApiError(status 0)`,
   JSON-тіло помилки → `code`/`message`/`details`, 204 → `undefined`, заголовок
   `content-type` тільки за наявності тіла. Чистий модуль, тест дешевий.
2. `client/src/lib/hooks/reviews.ts` — найскладніша логіка: `refetchInterval` як функція,
   SSE-накопичення, інвалідації. Це **страхувальна сітка для П.13**, тому пишеться
   раніше за нього.
3. `client/src/lib/hooks/core.ts` — інвалідації після мутацій
   (`useRefreshRepo` гасить і `repos`, і `pulls(repoId)`).
4. `client/src/lib/repo-context.tsx` і `theme.tsx` — обидва містять `setState` в ефекті
   (два з 13 наявних попереджень ESLint), тож тест зафіксує поточну поведінку перед тим,
   як їх виправлятимуть.

Сторінки (`page.tsx`) не покривати юнітами — їх покриває `e2e/specs/*.flow.json`; дублювати
дорого й крихко.

**Перевірка.**
```sh
pnpm --dir client test
```
Кількість тест-файлів: 14 → 18+. Покриття як число не ставити за мету — воно тут
дезорієнтує.

**Ризик.** `vitest.config.ts` задає `globals: true` і `environment: jsdom`; `EventSource`
у jsdom **немає**, тож для хуків із SSE потрібен стаб. Написати його один раз у
`src/test/setup.ts`, а не в кожному тесті.

**Залежності.** Блокує П.13 (за задумом). **Розмір.** M.
**Скіл:** `react-testing-library`.

## Питання до користувача

Чотири рішення, які план свідомо не приймає за користувача. Перші три названі в завданні,
четверте виявилось під час читання коду.

**1. П.9 — SPA чи RSC?**
Механіка `'use client'` — вимога фреймворку, але вибір архітектури — ні.
(а) Визнати SPA і виправити `client/AGENTS.md`, щоб конвенція не суперечила коду — дешево,
чесно, нічого не ламає.
(б) Пілот на одному маршруті з `prefetchQuery` + `HydrationBoundary`, заміряти, і лише
потім вирішувати про решту.
(в) Лишити як є й не чіпати документ — тоді конвенція лишається неправдою, і наступний
агент знову за неї спіткнеться.

**2. П.11 — яка система стилів канонічна?**
(а) Інлайнові стилі + `styles.ts` лишаються канон, Tailwind прибирається із залежностей
(мінус збірковий крок, який нічого не дає).
(б) Tailwind стає канон, інлайнові стилі мігрують поступально, по маршруту.
(в) Гібрид: інлайнові стилі лишаються, CSS-класи додаються **тільки** для станів
(`:hover`, `:focus-visible`) — мінімальний крок, що розблоковує П.10.

**3. П.14 — який обсяг i18n?**
(а) Усе, що бачить користувач, включно зі службовими підписами.
(б) Тільки продуктові екрани; службове лишається англійською, конвенція звужується.
(в) i18n заморожується як є, доки не зʼявиться друга локаль.

**4. Кому належить `client/src/vendor/ui`?**
Правило «не чіпати `src/vendor/**`, правити джерело» працює для `@devdigest/shared`
(джерело — `server/src/vendor/shared`), але для `@devdigest/ui` **джерела в репозиторії
немає**. Тобто 9 компонентів із hover-станом (і вся UI-бібліотека) зараз недоторканні за
правилом, яке неможливо виконати.
(а) Визнати `client/src/vendor/ui` first-party, прибрати його з «Do not touch» — тоді П.10
і П.11 поширюються на всю бібліотеку.
(б) Лишити недоторканним — тоді П.10 закриває рівно два компоненти, і це треба зафіксувати
як свідоме обмеження.
(в) Додати джерело (окремий пакет) і генерувати дзеркало — найдорожче, має сенс лише якщо
UI-кіт шариться з іншим проєктом.

## Чого цей план свідомо не робить

- **Не вмикає `typescript-eslint` у режимі з перевіркою типів.** `recommended-type-checked`
  знайде плаваючі проміси й небезпечні `any`, але дасть десятки нових попереджень і
  сповільнить `lint`. Це окреме рішення з власним базовим станом, а не причіп до П.1.
- **Не чіпає `modules/settings/feature-models.ts`**, хоч це справжній витік ORM. Він
  лікується винесенням `settings/repository.ts`, тобто своїм маленьким П.4 — і заслуговує
  окремого пункту, а не рядка в чужому батчі.
- **Не переводить `reviewer-core` з npm на pnpm** і не виносить `server/clones/`, хоч обидва
  є в `improvement-plan.md` як дрібниці. Вони не залежать ні від чого тут і робляться в
  будь-який момент; змішувати їх із архітектурними батчами — робити діфи нечитабельними.
- **Не пропонує метрику покриття тестами.** Число покриття тут дезорієнтує: 256 файлів
  фронту — здебільшого presentational-компоненти, де 80% покриття означало б тести на
  розмітку.
- **Не переписує `INSIGHTS.md`.** Файли append-only; усе, що цей план дізнався, додається
  новими датованими записами через скіл `engineering-insights`, коли відповідна робота буде
  зроблена — а не авансом.
- **Не планує самі рішення з розділу «Питання».** П.9, П.11, П.14 і доля `vendor/ui`
  лишаються з варіантами й без вироку — це прямо вимагає скіл `frontend-ui-architecture`:
  де немає авторитетного джерела, уподобання не подається як вимога.
