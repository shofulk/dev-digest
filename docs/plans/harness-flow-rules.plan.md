## Goal
Change the prompts and the Flow of four harness agents to close four recurring gaps: Verify cells that cannot fail (C1), plans that contradict themselves (C2), guard bypasses that surface only as non-gating hand-offs (C3), and manual acceptance items reported without evidence (C7). One more rule stops session-protocol outputs from landing as unplanned changes (C9).

## Acceptance criteria
1. **AC1 — Verify-cell rules (P1 a–c, plus d).** `.claude/agents/planner.md` *Procedure (create mode)* gets a new **Verify cells** step with four rules:
   - (a) A Verify names only commands and files that exist at `Base` or are created by an earlier step. It never names a file the Test plan defers.
   - (b) A step with several requirements (for example code plus its README half, or a removal) gets one Verify per requirement. A removal gets a negative grep.
   - (c) A Verify that proves a change was made must be able to fail on the pre-change code (example: the same `rg` over `git show <Base>:<path>` finds nothing). A guard-only Verify (for example append-only) says that it only guards.
   - (d) Each phrase a Verify requires verbatim gets its own single-phrase `rg`, because a multi-`-e` `rg` exits 0 when any one pattern matches. The step's Change says the phrase stays on one source line, because `rg` matches line by line and a hard wrap splits the phrase. *(rev 2)*
2. **AC2 — Self-consistency pass (P1 d).** `planner.md` gets a **Self-consistency pass** in both create mode and Update mode (new step `3a`). Before emitting, the planner re-derives every Verify cell and every Test-plan expectation against two things:
   - every other step or test that writes matching text;
   - the `bash checks` profile that plan-verifier runs under.

   In Update mode the pass covers the whole revised plan, not only the changed items.
3. **AC3 — Boundary questions become Test rows (P2 b).** In `planner.md`, a security question on a permission boundary (`scope-guard.sh`, `implementer-guard.sh`, `pr-gate.sh`) is emitted in two places:
   - as the *Review hand-off* line (as today);
   - also as a blocked Test-plan row: the exact bypass, fed through the full JSON dispatch, expected to be blocked.
4. **AC4 — `bypass-candidate` tag (P2 c).** In `.claude/agents/plan-verifier.md`, a *Handed off (not judged)* line about a possible bypass of one of the three boundary hooks starts with `bypass-candidate`. It still carries no severity, verdict or fix advice.
5. **AC5 — A reproduced bypass fails the round (P2 a, light variant).** `.claude/agents/README.md` (*Flow*: the diagram and *The fix loop*) says:
   - The main session reproduces every `bypass-candidate` through the full JSON dispatch.
   - A reproduced bypass fails the round exactly like "not met": retro-writer runs, then the fix loop.
   - A candidate that is not reproduced is recorded and does not fail the round.

   The Catalog note still says there is no security-reviewer agent. No new agent file is added.
6. **AC6 — Implementer reports manual items as `partial` (P6 a).** In `.claude/agents/implementer.md`, a step whose Verify (or an assigned Test row) includes anything outside the implementer's remit (a running stack, an e2e flow, a live agent probe) is reported `partial`, never `done`. The missing part goes under *Open issues* as a `manual acceptance:` line.
7. **AC7 — Manual acceptance step (P6 b).** `README.md` *Flow* adds an explicit main-session **Manual acceptance** step between the implementer (and test-writer) and the reviewers, both in the diagram and in prose:
   - It runs or delegates every `manual acceptance:` item.
   - It passes the results to plan-verifier as a `Manual acceptance:` block.
   - `plan-verifier.md` cites such a block as evidence for that item. Without the block, the item stays *cannot verify*.
   - README *Artifacts* lists the block as an optional plan-verifier input.
8. **AC8 — Standing session-protocol step (P8).** `planner.md` has one short rule: every plan ends with a standing **session-protocol step** that appends `INSIGHTS.md` entries through `engineering-insights`, so that entries map to a plan item instead of *Unplanned changes*.
9. **AC9 — Scope.**
   - Only the four agent files above change under `.claude/`, plus an optional append to root `INSIGHTS.md`.
   - Unchanged: agent frontmatter, `.claude/hooks/**`, `.claude/settings.json`, `.claude/skills/**`, every `CLAUDE.md`, `skills-lock.json`.
   - No edit in the sections plan B owns (C5).
