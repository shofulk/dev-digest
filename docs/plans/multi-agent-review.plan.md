# Development Plan: multi-agent-review

**Spec:** `specs/multi-agent-review.spec.md` (SPEC-03-multi-agent-review) · **Packages:** server, client, e2e · **Base:** 32db6e9 · **Revision:** 1 · **Execution mode:** multi-agent

## Goal
Let a reviewer pick several agents for a PR, run them in parallel under one capped multi-run, and compare and act on their findings in Columns and Tabs views with a "Where agents disagree" block, plus cancel, retry and Learn.

## Acceptance criteria

## Non-functional requirements and assumptions (copied from the spec; binding)
- **NFR-1** Reliability: the server shall run at most 3 agent runs at the same time by default. The cap shall be configurable with a minimum of 1, where 1 means one after another. *Verify: unit*
- **NFR-2** Cost: a multi-run of N agents shall make the same model calls as N single agent runs, and grouping, estimates and the read route shall make 0 model calls. *Verify: unit*
- **NFR-3** Performance: the start request shall answer within 500 ms at p95, because no agent work runs before the answer. *Verify: it*
- **NFR-4** Performance: the multi-run read route shall answer within 300 ms at p95 for 5 agents with 50 findings each on the seeded dataset. *Verify: it*
- **NFR-5** Limits: one multi-run shall hold at most 20 agents. *Verify: it*
- **NFR-6** Security: the multi-run code shall log only ids, counts, statuses and durations, with 0 log lines that contain finding text, prompts or diff content. *Verify: unit*
- **NFR-7** Accessibility: the picker checkboxes, the agent cards, the Columns / Tabs switch, the agent tabs and the conflicts toggle shall be reachable and usable with the keyboard, with 0 axe violations of level A or AA. *Verify: e2e*
- **NFR-8** i18n: every user-facing string of this feature shall come from `client/messages/en/*.json`. *Verify: unit*
- **A-1** One cap applies to the whole executor, across all PRs, and the default is 3.
- **A-2** The cap also applies to `POST /pulls/:id/review` with `all:true`, because both share one executor.
- **A-3** A waiting agent run (no free slot yet) shows the status `running`, and its live log says it waits for a slot.
- **A-4** Median is a useful estimate after a single run (sample size 1).
- **A-5** The memory row from Learn has no confidence value.
- **A-6** The PR-page picker lists every agent, including disabled ones, as the current menu does.
- **A-7** "Configure agents…" keeps its current target, the Agents page.
- **A-8** A new agent run of a multi-run uses the same run event stream and trace as a single run, so the existing live log and trace drawer work unchanged.

## Constraints
- **Architecture:** onion-architecture "The rings, by real path". New server files state their ring in the header: `modules/reviews/scheduling.ts`, `multi-run-helpers.ts`, `multi-run-service.ts` and `learn.ts` are ring 1. `modules/reviews/repository/multi-run.repo.ts` and `memory.repo.ts` are ring 2. `platform/run-limiter.ts` is ring 2, infra half like `jobs.ts`. `routes.ts` is ring 3. Ring-1 files never import `fastify`, `drizzle-orm` or `db/schema`, and never construct a ring-2 class. `MultiRunService` resolves everything in its constructor (`container.reviewRepo`, `container.agentsRepo`, `container.runBus`, a `ReviewRunExecutor` built from those plus `intentDeriverFor(container)`), with no `this.container.x` in method bodies. The executor resolves `container.agentRunLimiter` in its constructor. `scheduling.ts` declares its own structural limiter/logger types; it must not import `run-executor.ts`, to avoid a cycle. `pnpm --dir server arch` stays at 0 errors and ≤ 17 warnings. Client (frontend-ui-architecture): pages are thin, `'use client'` goes on the view, components read data only through `src/lib/hooks/*`, and pure logic lives in plain modules (no `use` prefix).
- **Contracts & data:** Zod is edited only in `server/src/vendor/shared/contracts/observability.ts` and `review-api.ts`. Both are copied byte for byte to `client/src/vendor/shared/contracts/`, and both are added to the parity list in `server/test/eval-contract-parity.test.ts`. `knowledge.ts` stays unchanged. Tables: fill `multi_agent_runs` (add nullable `head_sha text`) and `agent_runs` (add nullable `multi_agent_run_id uuid` → `multi_agent_runs.id` `on delete set null`, index `agent_runs_multi_idx`). Both go in `src/db/schema/runs.ts`, then `pnpm --dir server db:generate`. The change is ADD-only, so there is no rename prompt. `memory` gets its first writer (no column change). `findings`/`reviews` are read only. No new table.

- **Server decisions:**
  - **D1 Start route.** `POST /pulls/:id/multi-agent-run` (IdParams), route `config.rateLimit { max: 10, timeWindow: '1 minute' }` (AC-30). The body is parsed in the handler with `MultiAgentRunRequest.safeParse(req.body ?? {})`. Failure throws `new AppError('invalid_multi_run_request', …, 400)`, not `schema.body` (which answers 422). Order:
    1. 400 (AC-21, NFR-5, counted on the raw list).
    2. Pull in workspace, else 404 (AC-23).
    3. Dedupe ids, first seen wins.
    4. Every id must be a uuid and an agent of the workspace (enabled or not, AC-24), else 404 `Agent not found` (AC-22; a malformed id also answers 404).
    5. One repository transaction inserts the `multi_agent_runs` row (`head_sha` = pull.headSha) and one `running` `agent_runs` row per agent, linked.
    6. Answer 200 `MultiAgentRunStarted`.
    7. Then `void executor.executeRuns(…)`. The route never awaits agent work (AC-20, NFR-3).
  - **D2 Cap.** `REVIEW_AGENT_CONCURRENCY` (env, blank → default) → `AppConfig.reviewAgentConcurrency`, `z.coerce.number().int().min(1)`, default 3 (NFR-1). One `AgentRunLimiter` per Container: `container.agentRunLimiter`, lazy, wrapping the existing `p-queue` with `concurrency = reviewAgentConcurrency`. API: `constructor(concurrency: number)`, `readonly concurrency`, `run<T>(task: () => Promise<T>): Promise<T>`, `hasFreeSlot(): boolean`. Both routes run through `executeRuns`, so `all:true` is capped too (A-1, A-2).
  - **D3 Scheduling.** `scheduleAgentRuns(jobs, deps)` in `scheduling.ts`, where `deps = { limiter, isCancelled(runId), run(job), onWaiting(job), onSkipped(job), logger?, context: { prId, multiRunId? } }`. Jobs are enqueued in order. A job whose enqueue finds no free slot gets `onWaiting(job)`; the executor publishes the Live Log line `Waiting for a free agent slot` (A-3). When a slot is granted: if `isCancelled(runId)`, call `onSkipped(job)` and never `run(job)` (AC-44); otherwise call `run(job)`. Errors are isolated per job. It resolves when every job has settled. Each started job's model work starts only inside its slot (AC-25).
  - **D4 Cancel invariants (AC-43).** `RunBus.complete()` no longer deletes the cancel flag (`sse.ts:79`). `completeAgentRun` updates only rows whose status is still `running` and returns `Promise<boolean>`. `failAll` and the catch path keep calling it. The executor re-checks `isCancelled` after `reviewPullRequest` returns and before `insertReview`. `onSkipped` saves the trace from the bus buffer, calls `cancelRunIfRunning`, completes the bus, and never calls `container.llm`.
  - **D5 Diff failure (AC-28).** `loadDiff` throws `Error('PR diff unavailable: <git error message>')` when `git.diff` throws AND the `pr_files` fallback yields zero files. The existing `failAll` then fails every run with that one message. Diff and intent pre-work stays once per `executeRuns` call (AC-26).
  - **D6 Read.** `GET /multi-agent-runs/:id` (IdParams) answers 404 `Multi-agent run not found` when the row is absent or in another workspace (AC-35). The response:
    - **columns:** one per non-null `agent_id` among the multi-run's runs, built from that agent's newest run (`ran_at` desc, then `id` desc). Ordered by agent name (case-insensitive), then `agent_id`. The `status` is the stored status (`running`/`done`/`failed`/`cancelled`; any other value maps to `failed`). `verdict`/`summary` come from the run's review (null if none), `score = run.score ?? review.score`, plus `duration_ms`, `cost_usd`, `error`. `findings` are the review's persisted rows (AC-70, AC-41), mapped to `AgentColumnFinding` plus `learned`.
    - **agent_count:** `columns.length`.
    - **head_sha:** the stored value. **stale:** stored `head_sha` !== `pull.headSha` (AC-34).
    - **pr_number:** `pull.number`.
    - **Totals and conflicts:** from D7 over the column data.
    - **Queries:** at most one query per concern, with no per-finding query (NFR-4).
  - **D7 Helpers (`multi-run-helpers.ts`, pure, no LLM, no I/O).** Inputs are internal types: `GroupInputColumn = { agent_id; agent_name; status; findings: { id; severity: Severity; title; file; start_line; end_line }[] }` and `{ status; duration_ms; cost_usd }[]`.

## Risks / open questions
- **R1** Flow 13 starts real runs. It is deterministic only without a provider key (CI `e2e-web.yml`): each run fails at provider resolution before any model call. On a dev stack with keys it would make paid calls and reach `done` (no "Retry"). Affects T21 (Recommendation 7).
- **R2** `buildApp` reaps every `running` row on boot. A test that builds a second app while runs are gated flips them to `failed`. Affects T3–T6.
- **R3** `RunBus` is a process singleton. Keeping cancel flags (D4) grows a Set of run ids for the process lifetime (small). Affects S8.
- **R4** Learn idempotency is check-then-insert in one transaction with no unique constraint. Two concurrent first clicks can still write two rows (Recommendation 6). Affects S7/S11.
- **R5** NFR-3/NFR-4 timing assertions may flake on a loaded CI runner. Affects T3/T4.
- **R6** jsdom cannot evaluate colour contrast. NFR-7's AA contrast needs a manual axe DevTools pass on the picker, Configure run and results pages. Affects T15/T20.
- **R7** NFR-8 vs AC-18: the sidebar label "Multi-Agent Review" is a literal in vendor `nav.ts`, like every NAV label. Its `shell.json` twin `nav.multi-agent` already exists and drives the command palette. If NFR-8 is read as covering the sidebar label, that needs a superseding spec (spec-creator). Affects S17.
- **R8** `/pr-self-review` will raise a critical `vendor-mirror-edit` on `nav.ts`. Record `--override` citing the client INSIGHTS nav exception. Affects S17.
- **R9** D5 changes single-run behaviour too: a PR whose git diff fails and that has no stored patch now fails its runs instead of reviewing an empty diff. Affects S8.
- **R10** `POST /runs/:id/cancel` (existing, used for per-column Cancel) and `cancelRunIfRunning` are not workspace-scoped. This is pre-existing and handed to security review. Affects S21.
- **R11** `reviews.run_id` has no index. The multi-run read filters reviews by run ids; NFR-4 is expected to hold on the seeded dataset, but T4(h) is the proof. Affects S7.
- **R12** Client mirror: S1 copies whole files. `observability.ts`/`review-api.ts` are identical at Base; the pre-existing `productionize.ts` drift is out of scope. Affects S1.
