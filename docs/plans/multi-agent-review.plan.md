# Development Plan: multi-agent-review

**Spec:** `specs/multi-agent-review.spec.md` (SPEC-03-multi-agent-review); `specs/multi-agent-run-history.spec.md` (SPEC-04-multi-agent-run-history, added rev 2) · **Packages:** server, client, e2e · **Base:** a4008f2 · **Revision:** 3 · **Execution mode:** multi-agent

## Goal
Let a reviewer pick several agents for a PR, run them in parallel under one capped multi-run, compare and act on their findings in Columns and Tabs views with a "Where agents disagree" block, plus cancel, retry and Learn, and find earlier multi-runs again from a Recent runs list on the Configure run screen and an "Open multi-agent review" link on the PR page. *(rev 2)*

## Non-functional requirements and assumptions (copied from the spec; binding)
- **NFR-1** Reliability: the server shall run at most 3 agent runs at the same time by default. The cap shall be configurable with a minimum of 1, where 1 means one after another. *Verify: unit*
- **NFR-2** Cost: a multi-run of N agents shall make the same model calls as N single agent runs, and grouping, estimates and the read route shall make 0 model calls. *Verify: unit*
- **NFR-3** Performance: the start request shall answer within 500 ms at p95, because no agent work runs before the answer. *Verify: it*
- **NFR-4** Performance: the multi-run read route shall answer within 300 ms at p95 for 5 agents with 50 findings each on the seeded dataset. *Verify: it*
- **NFR-5** Limits: one multi-run shall hold at most 20 agents. *Verify: it*
- **NFR-6** Security: the multi-run code shall log only ids, counts, statuses and durations, with 0 log lines that contain finding text, prompts or diff content. *Verify: unit*
- **NFR-7** Accessibility: the picker checkboxes, the agent cards, the Columns / Tabs switch, the agent tabs and the conflicts toggle shall be reachable and usable with the keyboard, with 0 axe violations of level A or AA. *Verify: e2e*
- **NFR-8** i18n: every user-facing string of this feature shall come from `client/messages/en/*.json`. *Verify: unit*
- **A-1** One cap applies to the whole executor, across all PRs, and the default is 3.
- **A-2** The cap also applies to `POST /pulls/:id/review` with `all:true`, because both share one executor.
- **A-3** A waiting agent run (no free slot yet) shows the status `running`, and its live log says it waits for a slot.
- **A-4** Median is a useful estimate after a single run (sample size 1).
- **A-5** The memory row from Learn has no confidence value.
- **A-6** The PR-page picker lists every agent, including disabled ones, as the current menu does.
- **A-7** "Configure agents…" keeps its current target, the Agents page.
- **A-8** A new agent run of a multi-run uses the same run event stream and trace as a single run, so the existing live log and trace drawer work unchanged.
- **SPEC-04 numbering (rev 2):** SPEC-04 `AC-n` is plan `AC-(75+n)`. SPEC-04 NFRs and assumptions are prefixed `H-` so they never collide with SPEC-03's.
- **H-NFR-1** Performance: the list route shall answer within 200 ms at p95 for a repo with 500 multi-runs of 5 agent runs each. *Verify: it*
- **H-NFR-2** Cost: the list route shall make 0 model calls and 0 GitHub calls. *Verify: unit*
- **H-NFR-3** Limits: the list shall return and the client shall render at most 20 rows. *Verify: it + unit*
- **H-NFR-4** Security: the list code shall log only ids, counts, statuses and durations, with 0 log lines that contain a PR title. *Verify: unit*
- **H-NFR-5** Accessibility: every Recent runs row and the "Open multi-agent review" link shall be reachable with Tab and usable with Enter, with 0 axe violations of level A or AA on the Configure run screen. *Verify: e2e*
- **H-NFR-6** i18n: every user-facing string of this feature shall come from `client/messages/en/*.json`. *Verify: unit*
- **H-A-1** A fixed limit of 20 rows is enough to find a recent multi-run, and older runs do not need to be reachable from the list.
- **H-A-2** One route serves both entry points: the PR page uses the `pr_id` filter and takes the first item.
- **H-A-3** A `cancelled` agent run counts as "not done" for the status, the same as `failed`.
- **H-A-4** The status names `running`, `done`, `partial`, `failed` and their labels "Running", "Done", "Partial", "Failed" match what the user means by "running / done / partial-failed".
- **H-A-5** The list shows the start time as a relative time ("5 min ago") with the full date and time on hover.
- **H-A-6** A row is one link that opens the results page in the same tab.
- **H-A-7** The PR page link sits in the PR header actions, next to the Review menu, and is shown for a running multi-run too.
- **H-A-8** A refresh every few seconds while a row is running is cheap enough, because the route reads only the DB (H-NFR-1, H-NFR-2).
- **H-A-9** The 200 ms p95 target follows SPEC-03 NFR-4 (300 ms for one full multi-run read); the list reads no findings, so it is lighter.
- **H-A-10** The results page breadcrumb "Multi-Agent Review › #<PR number>" already exists; plan AC-101 pins it so a later change does not break the way back.

## Recommendations
1. Q-3: join the existing `GET /pulls/:id/reviews` read in the Tabs view instead of widening `AgentColumnFinding`. The reviews read already carries every Tabs field plus `accepted_at`/`dismissed_at`/`review_id`, which AC-57/AC-58 need and which the spec's `AgentColumn` contract does not list. Accept/dismiss already invalidates `["reviews", prId]`. · cost: one extra read on the results page · applied as S22 (C6).
2. Keep all new server routes in `server/src/modules/reviews/routes.ts`. ## Risks / open questions
- **R1** Flow 13 starts real runs. It is deterministic only without a provider key (CI `e2e-web.yml`): each run fails at provider resolution before any model call. On a dev stack with keys it would make paid calls and reach `done` (no "Retry"). Affects T21 (Recommendation 7).
- **R2** `buildApp` reaps every `running` row on boot. A test that builds a second app while runs are gated flips them to `failed`. Affects T3–T6.
- **R3** `RunBus` is a process singleton. Keeping cancel flags (D4) grows a Set of run ids for the process lifetime (small). Affects S8.
- **R4** Learn idempotency is check-then-insert in one transaction with no unique constraint. Two concurrent first clicks can still write two rows (Recommendation 6). Affects S7/S11.
- **R5** NFR-3/NFR-4 timing assertions may flake on a loaded CI runner. Affects T3/T4.
- **R6** jsdom cannot evaluate colour contrast. NFR-7's AA contrast needs a manual axe DevTools pass on the picker, Configure run and results pages. Affects T15/T20.
- **R7** NFR-8 vs AC-18: the sidebar label "Multi-Agent Review" is a literal in vendor `nav.ts`, like every NAV label. Its `shell.json` twin `nav.multi-agent` already exists and drives the command palette. If NFR-8 is read as covering the sidebar label, that needs a superseding spec (spec-creator). Affects S17.
- **R8** `/pr-self-review` will raise a critical `vendor-mirror-edit` on `nav.ts`. Record `--override` citing the client INSIGHTS nav exception. Affects S17.
- **R9** D5 changes single-run behaviour too: a PR whose git diff fails and that has no stored patch now fails its runs instead of reviewing an empty diff. Affects S8.
- **R10** `POST /runs/:id/cancel` (existing, used for per-column Cancel) and `cancelRunIfRunning` are not workspace-scoped. This is pre-existing and handed to security review. Affects S21.
- **R11** `reviews.run_id` has no index. The multi-run read filters reviews by run ids; NFR-4 is expected to hold on the seeded dataset, but T4(h) is the proof. Affects S7.
- **R12** Client mirror: S1 copies whole files. `observability.ts`/`review-api.ts` are identical at Base; the pre-existing `productionize.ts` drift is out of scope. Affects S1.
- **R13** `Base` `a4008f2` predates the uncommitted SPEC-03 tree. `git diff a4008f2` guards (INSIGHTS append-only, migrations) see SPEC-03's changes too, and `git show a4008f2:` controls for SPEC-03-created files fail because the file is absent. Both stay valid under the *Failing-first convention*, but a reviewer must read them that way (Recommendation 10). Affects S26–S40.
- **R14** agent-browser locators cannot assert row *order*. T32 is deterministic only on a fresh seed, where flow 13 creates the only multi-runs of #482 and its first run is the only row. AC-97's "first row" and AC-100's "newest" are proven by T24(a)/T25/T29. On a reused DB the flow still passes, so it may prove less. Affects T32.
- **R15** The new query on `ConfigureRunView` makes the existing SPEC-03 tests (`ConfigureRunView.test.tsx`, `multi-agent-a11y.test.tsx`) request `/repos/<id>/multi-agent-runs` through their fetch mocks. S37 adds only a fixture answer; any other edit there is out of scope. Affects S37.
- **R16** H-NFR-1's p95 ≤ 200 ms with 2,500 seeded agent runs may flake on a loaded CI runner. Affects T24(j).
- **R17** Relative time and the hover title depend on `now` and the time zone. A test without a fixed `now` and an explicit `timeZone` will be flaky or log next-intl `ENVIRONMENT_FALLBACK`. Affects T28/T31.
- **R18** H-NFR-5's "Tab and Enter" is proven in RTL (T29/T31 with `user-event`). The e2e uses link-role locators, because agent-browser has no focus-and-press step for links (e2e INSIGHTS: `find role button focus` does not exist), and colour contrast stays a manual axe DevTools pass on Configure run. Affects T31/T32.
- **R19** While a row is `running`, both the Configure run list and the PR-page link query poll every 3 s (H-A-8). The cost is two DB-only reads per open tab. Affects S36.
