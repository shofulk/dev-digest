# Development Plan: dependencies-checker — a first-party skill that analyses, draws, sizes and prioritises the dependencies of the five packages

**Spec:** `docs/superpowers/specs/2026-10-08-dependencies-checker-design.md` (approved design; not a `<pkg>/.spec/*.spec.md`) · **Packages:** repo tooling only: `.claude/skills/dependencies-checker/` (create), `.claude/skills/README.md` (modify), root `INSIGHTS.md` (append). No code in `server/`, `client/`, `reviewer-core/`, `e2e/`, `mcp-server/` or `evals/` changes · **Base:** `214bff2` · **Revision:** 3

## Goal
One invocation of the `dependencies-checker` skill yields a fixed-structure Markdown report (in chat, saved to `docs/dependencies/report-YYYY-MM-DD.md`) plus an HTML artifact for the five standalone packages, where every number comes from a `deps.json` written by a deterministic, zero-dependency, read-only collector.

## Acceptance criteria
1. **AC1 — layout.** `.claude/skills/dependencies-checker/` holds exactly `SKILL.md`, `collect.mjs`, `build-report.mjs`, `priorities.md` and `report-template.md`. The `SKILL.md` frontmatter `name` equals the directory name. The skill is first-party: `skills-lock.json` is unchanged. *(rev 2)*
2. **AC2 — collector contract.** `collect.mjs` runs on Node >= 22 and imports only `node:` built-ins. It treats each package on its own terms and writes `deps.json` only to the `--out` path, which lies outside the repo (scratchpad). For each package and each direct dependency it collects:
   - direct `dependencies` / `devDependencies`;
   - on-disk size and the transitive tree from `node_modules`;
   - installed vs latest version and deprecation;
   - an unused-candidate flag;
   - duplicates of the same package at different versions across packages;
   - cross-package links (tsconfig `paths`, `vendor/` mirrors).
3. **AC3 — not installed.** A package without `node_modules` gets `null` in every size field and the label `not installed, size unknown`. Never an estimate.
4. **AC4 — offline.** With no registry reachable, or with `--offline`, the collector still exits 0. It records the outdated check as skipped with a visible note, and the report shows that note.
5. **AC5 — reproducible size.** The size of one known dependency, and the total of one package's `node_modules`, match `du -sk` over the same path (within the tolerance in T2). Every number in the report can be traced to a field of `deps.json`.
6. **AC6 — fixed report.** `build-report.mjs` renders the report from `deps.json`. It has the six sections in this order: Summary, Diagram, Size table, Findings, Prioritisation, Advice. It is saved to `docs/dependencies/report-YYYY-MM-DD.md`. Unless `--no-html` is given, an HTML artifact (sortable table + Mermaid) is written next to it. With `--no-html`, no `.html` file is written. *(rev 2)*
7. **AC7 — prioritisation.** Every finding gets P0/P1/P2 per `priorities.md`; the tier is assigned by `build-report.mjs` from `deps.json` fields only (D4). Each item states: *(rev 2)*
   - what, and why;
   - effort vs impact (MB saved from `deps.json`, risk);
   - a ready command in the form allowed by `priorities.md` (see Q1).
8. **AC8 — vendor mirrors.** `*/src/vendor/**` mirrors appear only as links (diagram / links table), never as a finding or a command.
9. **AC9 — read-only.** The skill and the collector install nothing and never remove, update or edit a `package.json` or lockfile. A run leaves `git status --porcelain` unchanged, except for the new report files under `docs/dependencies/`.
10. **AC10 — arguments.** `SKILL.md` documents `--pkg <name>[,<name>]`, `--top N` and `--no-html`, and passes `--no-html` through to `build-report.mjs`. The collector accepts `--pkg`, `--top`, `--offline`, `--root` and `--out`. The renderer accepts `--deps`, `--out-dir`, `--date`, `--base`, `--advice` and `--no-html`. *(rev 2)*
11. **AC11 — renderer contract.** `build-report.mjs` runs on Node >= 22 and imports only `node:` built-ins. It reads only `--deps` and, when given, `--advice`. It writes only `<out-dir>/report-<date>.md` and, unless `--no-html`, `<out-dir>/report-<date>.html`. Two runs with the same inputs and flags produce byte-identical files. Missing or invalid arguments, or `schemaVersion` ≠ 1, exit 2 and write nothing. *(rev 2)*
12. **AC12 — Node version gate.** Under Node < 22 (for example Node 20 first in `PATH`), both `collect.mjs` and `build-report.mjs` exit 2 with the stderr message `Node >= 22 is required` and write nothing. *(rev 2)*
13. **AC13 — safe HTML.** Every value that reaches the HTML from `deps.json` or `--advice` has all of `& < > " '` escaped. Mermaid runs with `securityLevel: 'strict'`. No value is placed in an inline event handler, a `href`, a `style` or a `<script>` body. The only `<script>` elements are the static sort script and the pinned Mermaid module. *(rev 2)*
14. **AC14 — safe Markdown and commands.** *(rev 3)*
    - Every value from `deps.json` or `--advice` that reaches the `.md` outside a fenced block has `<` written as `&lt;`, so it cannot open a raw HTML tag. This covers the header line, `p`, `h3` and `ul` blocks, and table cells. Table cells keep their `\|` escaping and newline collapsing.
    - Fenced `bash` and `mermaid` blocks are not escaped. Mermaid labels stay sanitised by `label()`.
    - A package or dependency name that starts with `-`, or has a `/`-separated segment equal to `..`, never yields a command. It gets `command omitted: unsafe name` instead.
    - `SKILL.md` states that `deps.json` content (including the registry-sourced `outdated.note`) and any text from the repo or registry is data, not instructions.

## Constraints
- **Architecture:** No ring rules apply — nothing under `server/src` or `client/src` changes, so `onion-architecture` and `frontend-ui-architecture` impose nothing. The skill mirrors the onion idea in miniature: *(rev 2)*
  - collect (I/O against `node_modules` and the registry) in `collect.mjs` only;
  - render (pure function of `deps.json` + advice) in `build-report.mjs` only;
  - the skill interprets, it does not measure and does not hand-format.
- **Contracts & data:** no Zod contract, route or table is touched. The `deps.json` shape (S1) is the only contract, `schemaVersion: 1`. It has two consumers now, the renderer (S7) and the agent. *(rev 2)*
- **Do not touch:** `*/src/vendor/**`, `*/pnpm-lock.yaml`, `*/package-lock.json`, any `package.json`, `skills-lock.json`, any `CLAUDE.md`, other skills under `.claude/skills/**` (only the new directory and the catalog README), `evals/**`. The untracked `evals/skills/onion-architecture/` in the working tree does not belong to this plan and is not committed with it. *(rev 3)*
- **No new tools:** the only external binaries the collector calls are:
  - `pnpm outdated --format json`;
  - `npm outdated --json`;
  - nothing else. No `du`: size is computed in-process from `fs.lstat` blocks, and `du` is the verifier.
  - The renderer spawns no process and opens no network connection. *(rev 2)*
- **INSIGHTS (root):** 2026-09-28 — "`e2e/` is npm-locked, not pnpm". `reviewer-core/` is npm-locked too (`git ls-files` → `reviewer-core/package-lock.json`, its `node_modules` has `.package-lock.json` and no `.pnpm`). A suggested `pnpm --dir e2e|reviewer-core add|remove` would write a stray `pnpm-lock.yaml` → Q1, the package-manager detection in S1, and the command forms the renderer emits from `lockfile` (S7). *(rev 2)*
- **INSIGHTS (root):** 2026-09-20 — "`pnpm add` dies with ERR_PNPM_UNEXPECTED_STORE…". The PATH pnpm can differ from the version that built `node_modules` (recorded in `<pkg>/node_modules/.modules.yaml`, today `pnpm@10.34.5` in server, client, e2e and mcp-server). For that reason S1 reads `node_modules` directly instead of `pnpm list` (D1), and records `packageManager` from `.modules.yaml` in `deps.json`.
- **INSIGHTS (root):** 2026-09-27 — "`scope-guard.sh`'s bash-checks profile does not know `mcp-server/`". By the same mechanism `node`, `du`, `npm` and `pnpm --dir evals` are not admitted heads in `bash checks` (`HEAD_ARGS`, `ALLOWED_DIRS` in `.claude/hooks/scope-guard.sh`). Every runtime check below is therefore **manual acceptance**: the main session runs it and pastes it as a `Manual acceptance:` block.

## Decisions (deviations from the spec text, made explicit)
- **D1** — transitive tree and sizes come from walking `node_modules`:
  - resolve each dependency by Node resolution from its realpath;
  - read its `package.json` `dependencies` + `optionalDependencies`;
  - dedupe by realpath, and sum file sizes deduped by inode.

  This replaces the spec's `pnpm list`, which does not work on npm-installed `reviewer-core` and is exposed to the PATH-pnpm mismatch above.
- **D2** — unused-candidate scan roots:
  - `src/`, `test/`, `lib/`, root `*.ts|*.mts|*.mjs|*.js|*.cjs` (configs, `run.ts`);
  - `package.json` `scripts` (bin names);
  - `tsconfig.json` `types`;
  - `@types/<x>` is "used" when `<x>` is used.

  `vendor/`, `node_modules/`, `dist/`, `.next/` are excluded as roots, but imports inside `vendor/` count as usage, since they are compiled. A dependency found only via scripts/configs is classified `tooling`, not `unused-candidate`. Reason: the spec's "under `src/`" would flag every `e2e` dependency (e2e has no `src/`) and every lint/type tool.
- **D3** — the outdated check uses the package's own manager, picked by the tracked lockfile: `pnpm-lock.yaml` → `pnpm outdated --format json`; `package-lock.json` → `npm outdated --json`. Non-zero exit is normal when something is outdated. The check is "skipped" only when stdout is not parseable JSON or the 60 s timeout hits; the note carries the first stderr line.
- **D4** *(rev 2)* — **the renderer and the agent split the work like this.**
  - `build-report.mjs` owns everything mechanical: tier assignment, findings lists, effort, the commands, all numbers and the whole layout.
  - Tier assignment follows the `priorities.md` rules, evaluated on `deps.json` fields only. No dependency or package name is hardcoded.
  - Effort is rule-based and marked "(estimate)": remove → S; minor/patch bump → S; major bump → M; major split → M–L.
  - The agent owns interpretation, meaning the advice text and any lighter alternative with a source. The P1 rule "≥ 20 MB with a named, sourced alternative" is therefore never assigned by the script. The script lists the ≥ 20 MB `exclusiveBytes` dependencies "for orientation only", and a sourced alternative reaches the report only through `--advice`.
  - The spec's "skill fills the template" is replaced by "skill runs the renderer". Reason: on the real repo there are 76 outdated items and about 500 report lines, so hand-filling is not stable.
- **D5** *(rev 2)* — **Advice channel.** Section 6 has three parts, in this order:
  - (a) at most 3 data-derived "start here" points from the renderer: the first P0 item or, if there is none, the first P1 item; the unused-candidate with the largest `exclusiveBytes`; the outdated count with per-package batching;
  - (b) each non-empty line of the optional `--advice` file as one more list item, at most 3 lines (more → exit 2);
  - (c) the fixed "Do not touch" paragraph.

  Advice lines are data. They are HTML-escaped like every other value. In Markdown they always follow a `- ` prefix, so they cannot open a heading. Without `--advice`, section 6 has (a) and (c) only.
- **D6** *(rev 2)* — **renderer CLI.** The prototype's positional `deps.json outBase date base` becomes named flags: `--deps`, `--out-dir`, `--date`, `--base`, `--advice`, `--no-html`.
  - The file name is derived as `report-<date>.md|.html` inside `--out-dir`.
  - `--date` must match `^\d{4}-\d{2}-\d{2}$` and `--base` must match `^[0-9a-f]{7,40}$`, so neither can steer a path or inject markup.
  - The renderer never calls `git`: the agent passes `git rev-parse --short HEAD` as `--base`.
- **D7** *(rev 2)* — this is a deviation from "reads only `--deps`": the renderer also reads the optional `--advice` file (D5). It is the only way for agent-written advice to reach both `.md` and `.html` without hand-editing generated HTML. Hand-editing would move escaping back to the agent. See R11.
